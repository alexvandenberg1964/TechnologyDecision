## 1. Purpose

Every question in the model scores each answer option against three platforms (`lc` = Low-Code, `hy` = Hybrid, `hc` = High-Code) on a 0–3 scale, and every question carries a default weight (1–3). Those numbers currently live only as bare object literals in `lowcode-decision-model.html` (`HARD_RULES`, `QUICK_SCAN`, `FULL_CATS`, `ORG_READINESS_CHECKS`) with no recorded justification beyond the short `desc` string shown in the UI.

This register is the single source of truth for **why each value is what it is**. It exists so that:

- an architect challenged on "why does this answer score `hc:3` and not `hc:2`?" can point to a recorded, panel-reviewed reason instead of "that seemed right at the time";
- a change to a score value is a reviewed, versioned decision, not a silent edit to a JS array;
- new questions are calibrated against the same explicit method as existing ones, not just "by feel."

## 2. Governance process

1. **Propose** — open a PR that changes a value in the model *and* the corresponding row in this register in the same commit. A code-only change to a score/weight without a matching register update should be rejected in review.
2. **Panel review** — at least **2 of 3** designated architecture-panel members (see §4) approve the PR. For a `ko`/`block` hard constraint (Layer 1) or an `ORG_READINESS_CHECKS` base weight, require all 3.
3. **Record** — add a row to the changelog (§3) with date, what changed, from → to, who approved, and why. Bump the document version (`vX.Y`): `Y` for a single value tweak, `X` for a structural change (new question, new rule, re-tiering a whole category).
4. **Annual revisit** — reviewed on the same cadence as the model itself (see review finding 2.5 — annual revision cycle), even if no PRs came in, to catch drift between the model and current PostNL platform reality (pricing, platform capability changes, org changes).

Until step 2 has actually happened for a given row, that row is marked **Draft** in the Status column below. **Draft** means: "this is the reasoning implied by the current code, reconstructed for review — not yet confirmed by anyone but the tool's author."

## 5. How to read the tables

- **lc / hy / hc** — points (0–3) awarded to that platform if this option is chosen. Higher = stronger signal toward that platform.
- **Δ (spread)** — the gap between the highest and lowest score in the row. A wide spread (e.g. `3/0/0`) means the answer is treated as a strong, near-exclusive signal; a narrow spread (e.g. `2/2/1`) means the answer is treated as weakly discriminating.
- **Status** — `Draft` (reconstructed, unreviewed) or `Confirmed vX.Y` (panel-approved, with the version it was confirmed in).
- **Rationale** — the reasoning, extended from the in-UI `desc` field with the explicit "why this number and not one point higher/lower" logic that the UI text doesn't have room for.

## 7. Quick Scan (`QUICK_SCAN`)

Quick Scan questions are intentionally coarser than Full Assessment (3–4 options, wide spreads) because the whole point of a 5-question scan is a fast directional signal, not defensible precision. Default weight is `2` for all five *except* `qs_ui` (now `3`, see below) — otherwise flat, because with only 5 questions there is no basis yet for saying one matters more than another; that's arguably itself worth panel scrutiny (see open item in §9).

**Former known defect (review finding 4.2) — ✅ fixed in code, not just tracked here:** `team_skills` (and `qs_capability`, which had the identical shape) used to reward *either* a strong Low-Code *or* a strong High-Code team as "ready" via a fixed `goodIdx:[0,3]` list, regardless of which platform the Technology Fit score actually recommended. Both checks now use `relativeToWinner:true`: readiness is computed by comparing the answered option's own `lc`/`hy`/`hc` score triple (the same shape every Technology Fit question already uses) against `winner.key` — "ready" means the winning platform is that option's strongest fit. A full-stack/Hybrid-shaped team (`team_skills` index 2) that used to be marked "not ready" even on a Hybrid-winning project now correctly reads as ready; a strong Low-Code team on a High-Code-winning project now correctly reads as not ready. Regression-pinned in `tests/fixtures/edge-case-scenarios.js` (3 new scenarios) — see `tests/run-tests.js`. This was a logic bug, not a value-calibration question, so it did not require a version bump of the *scoring* values above; the base weights (14 for each) are unchanged and remain Draft.
